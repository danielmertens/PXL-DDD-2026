Lab 9 — Projections

Oplossing

Dag 2/Result krijg je op het einde van de dag

Opdracht

  1. Implementeer een projection service
  2. Query data via projections i.p.v. aggregates

Waarom projections?

  • Je splitst gedrag (commands op aggregates) van queries (CQRS)
  • Een projection is een model dat speciaal voor het lezen gebouwd wordt, los van je aggregate
  • Handig wanneer je met event sourcing werkt: een aggregate laden om te lezen is dan duur

Stappen

  1. Ontwerp een read-model, bv. AlbumOverviewProjection (id, albumnaam, publicatiejaar)
  2. Schrijf een projection service met een methode per gebeurtenis, bv. OnAlbumUpdated
  3. Laat je handler uit oefening 8 die service aanroepen: zo wordt de projection bijgewerkt bij elke wijziging
  4. Voeg een endpoint toe dat de projection leest, niet de aggregate

Het read-model en zijn poorten

Een platte klasse, zonder value objects of gedrag:

// HarmonyTunes.Catalogue/Album/Projection/Models/AlbumOverviewProjection.cs
public class AlbumOverviewProjection
{
    public Guid Id { get; set; }                            // = AlbumReference.Key
    public string AlbumName { get; set; } = string.Empty;
    // ... enkel wat je lees-scherm nodig heeft
}
// HarmonyTunes.Catalogue/Album/Projection/Interfaces
public interface IAlbumProjectionsService
{
    Task OnAlbumUpdated(AlbumReference albumReference);
}

public interface IAlbumProjectionsRepository
{
    void AddOrUpdateProjection(AlbumOverviewProjection projection);
    Task Commit();
}

Voor het lezen voeg je zelf een methode of een aparte query-interface toe.

De handler en het lees-endpoint

MassTransit maakt per bericht een DI-scope, dus je consumer krijgt scoped services gewoon via de constructor:

public class AlbumUpdatedNotificationHandler : IConsumer<AlbumUpdatedNotification>
{
    private readonly IAlbumProjectionsService _projections;

    public AlbumUpdatedNotificationHandler(IAlbumProjectionsService projections)
    {
        _projections = projections;
    }

    // Consume: roep _projections aan met de AlbumReference uit context.Message
}
app.MapGet("/api/albums/overview", async (/* jouw lees-interface */) =>
{
    // lees AlbumOverviewProjection; geen IAlbumRepository, geen aggregate
});

Let op

  • De projection opbouwen mag uit de aggregate (via de repository); het lees-endpoint raakt de aggregate niet aan
  • Upsert, geen insert: bestaat de rij al, overschrijf ze dan (_context.Entry(bestaande).CurrentValues.SetValues(nieuwe)); zo blijft je handler idempotent
  • Create en update kort na elkaar geven twee berichten die tegelijk verwerkt kunnen worden: beide vinden nog geen rij en doen een insert, de tweede botst op de primary key. De UseMessageRetry uit oefening 8 probeert opnieuw en dan wordt het een update

Controleer

Een lees-endpoint geeft de projection terug zonder dat de aggregate geladen wordt. Na een update via de api klopt de projection (na een korte vertraging, eventual consistency).

Klaar wanneer

je query-flow via de projection loopt en je aggregate niet meer aangesproken wordt voor lezen.
